# Supabase schema

**Supabase project:** `notes-lab` (project ref `zofotoflnohpjhfpodgb`, region `eu-central-1`, Postgres 17).
This is the project the local repo is linked to with the Supabase CLI.

Tables in the `public` schema. Read from the live database with the Supabase CLI on 2026-11-28,
after migration `20261128081958_fix_note_tags_primary_key.sql` was applied (columns, comments, constraints,
indexes, policies and triggers checked).

All IDs are `bigint` identity columns (`GENERATED BY DEFAULT AS IDENTITY`): the database fills them in
automatically when a row is added.

## Relationships in plain English

- **Users own their data:** every row in all four tables has a `user_id` (→ `auth.users.id`). Each signed-in
  user sees and changes only their own rows. Deleting a user deletes all their rows.
- **No links across users:** a note can only be in its owner's collection, and `note_tags` can only link a
  note and a tag of the same user (composite foreign keys on `(id, user_id)`).

- **Notes and collections:** a note can belong to one collection, or to none. A collection holds many notes.
  If a collection is deleted, its notes are kept and simply no longer belong to any collection.
- **Notes and tags:** a note can have many tags, and a tag can be on many notes. The `note_tags` table
  records each pairing ("this note has this tag").
  - The same tag can't be added to the same note twice.
  - If a note is deleted, its tag pairings are deleted too. The tags themselves stay.
  - If a tag is deleted, it is removed from every note. The notes themselves stay.
- **Tags** have unique names per user: one user can't have two tags called the same thing, but two users can each have a "work" tag. Each tag has a colour from a fixed palette of 8.

```
collections 1 ──< notes >── note_tags ──< tags
           (optional)        (many-to-many)
```

## Tables

"Can be empty?" means whether the column may be left `NULL`.

### `notes`

| Column | Type | Can be empty? | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | no | identity | Primary key |
| `user_id` | `uuid` | no | `auth.uid()` | Owner. → `auth.users.id`, `ON DELETE CASCADE` |
| `collection_id` | `bigint` | **yes** | | The collection this note is in; empty = no collection. → `collections (id, user_id)`, so it must be the owner's own collection. `ON DELETE SET NULL (collection_id)`: only `collection_id` is cleared |
| `title` | `text` | no | | |
| `body` | `text` | **yes** | `''` (empty text) | |
| `created_at` | `timestamptz` | no | `now()` | |
| `updated_at` | `timestamptz` | no | `now()` | Set to `now()` automatically on every update by trigger `notes_set_updated_at` |

### `collections`

| Column | Type | Can be empty? | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | no | identity | Primary key |
| `user_id` | `uuid` | no | `auth.uid()` | Owner. → `auth.users.id`, `ON DELETE CASCADE` |
| `name` | `text` | no | | Must not be blank: spaces only are rejected (`char_length(trim(name)) > 0`) |
| `created_at` | `timestamptz` | no | `now()` | |

### `tags`

| Column | Type | Can be empty? | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | no | identity | Primary key |
| `user_id` | `uuid` | no | `auth.uid()` | Owner. → `auth.users.id`, `ON DELETE CASCADE` |
| `name` | `text` | no | | Unique per user: (`user_id`, `name`), constraint `tags_user_id_name_key`. Case-sensitive in the database; the app also treats "work" and "Work" as the same tag |
| `color` | `text` | no | `'blue'` | Display colour. Must be one of `red`, `orange`, `yellow`, `green`, `teal`, `blue`, `purple`, `pink` (check `tags_color_check`). Added by migration `20261125091038_tags_color.sql`; the app's palette is in `lib/tag-colors.ts`. Column comment: the same list of colours and the palette path (set by migration `20261125094658_tags_color_comment.sql`) |

### `note_tags`

| Column | Type | Can be empty? | Default | Notes |
|---|---|---|---|---|
| `note_id` | `bigint` | no | | → `notes (id, user_id)`, `ON DELETE CASCADE` |
| `tag_id` | `bigint` | no | | → `tags (id, user_id)`, `ON DELETE CASCADE` |
| `user_id` | `uuid` | no | `auth.uid()` | Owner. → `auth.users.id`, `ON DELETE CASCADE` | Must match the note's and the tag's owner |

Primary key: (`user_id`, `note_id`, `tag_id`), plus unique (`note_id`, `tag_id`), so each note–tag pair appears only once.

`user_id` must be in the primary key: the Data API (PostgREST) only treats `note_tags` as the join table between
`notes` and `tags` (so `notes?select=id,tags(...)` works) when all its foreign key columns are part of its primary key.
Migration `20261128081958_fix_note_tags_primary_key.sql` fixed this after `20261128080010` had broken it.

`collections`, `notes` and `tags` also have a unique (`id`, `user_id`) constraint, which the composite foreign keys above point to.

| Table | Trigger | What it does |
|---|---|---|
| `notes` | `notes_set_updated_at` | Before every update, sets `updated_at` to `now()` (function `public.set_updated_at()`) |

## Access (row-level security)

RLS is enabled on all four tables. Access needs both a table grant and a policy.

Set by migration `20261128080010_add_user_ownership.sql`, which replaced the temporary open policies.

| Table | Grants (`anon`, `authenticated`) | Policies (role `authenticated` only) |
|---|---|---|
| `notes` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | `notes: select own / insert own / update own / delete own` |
| `collections` | same | `collections: … own` |
| `tags` | same | `tags: … own` |
| `note_tags` | same | `note_tags: … own` |

Every policy checks `(select auth.uid()) = user_id`; update policies check it on both the old and the new row,
so a row can't be handed to another user. There are no policies for `anon`, so signed-out visitors see no rows
and can't add any. Each table has an index starting with `user_id` (for `tags`, the unique (`user_id`, `name`) index; for `note_tags`, its primary key).

## Known issues

- **Leftover names on `collections`.** Its primary key (`notes_pkey`) and check constraint (`notes_title_check`) are named after `notes`. This suggests the table was renamed from an earlier `notes` table. The `notes` table's own primary key is therefore `notes_pkey1`.
- **Foreign keys without indexes.** `notes (collection_id, user_id)` and `note_tags (tag_id, user_id)` have no index. Listing a collection's notes, or finding all notes with a tag, will slow down as the tables grow.
- **The migrations can't rebuild these tables.** The four tables were created in the dashboard, and no file in `supabase/migrations/` creates them. Migration `20261124114513` only adds grants, policies and the trigger to existing tables. `npx supabase db pull` can generate a migration that captures the table definitions.

## Regenerating this document

Read-only queries with the Supabase CLI, for example:

```bash
npx supabase db query --remote --read-only -o table \
  "select table_name, column_name, data_type, is_nullable, column_default
   from information_schema.columns where table_schema = 'public'
   order by table_name, ordinal_position"
```

Also check:
- `pg_constraint`: keys, foreign keys, checks
- `pg_indexes`: indexes
- `pg_policies`: RLS policies
- `has_table_privilege()`: grants
- `pg_trigger`: triggers
