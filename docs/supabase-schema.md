# Supabase schema

**Supabase project:** `notes-lab` (project ref `zofotoflnohpjhfpodgb`, region `eu-central-1`, Postgres 17).
This is the project the local repo is linked to with the Supabase CLI.

Tables in the `public` schema. Read from the live database with the Supabase CLI on 2026-11-25,
after migration `20261125094658_tags_color_comment.sql` was applied (columns, comments, constraints,
indexes, policies and triggers checked).

All IDs are `bigint` identity columns (`GENERATED BY DEFAULT AS IDENTITY`): the database fills them in
automatically when a row is added.

## Relationships in plain English

- **Notes and collections:** a note can belong to one collection, or to none. A collection holds many notes.
  If a collection is deleted, its notes are kept and simply no longer belong to any collection.
- **Notes and tags:** a note can have many tags, and a tag can be on many notes. The `note_tags` table
  records each pairing ("this note has this tag").
  - The same tag can't be added to the same note twice.
  - If a note is deleted, its tag pairings are deleted too. The tags themselves stay.
  - If a tag is deleted, it is removed from every note. The notes themselves stay.
- **Tags** have unique names: there can't be two tags called the same thing. Each tag has a colour from a fixed palette of 8.

```
collections 1 ──< notes >── note_tags ──< tags
           (optional)        (many-to-many)
```

| Table | Trigger | What it does |
|---|---|---|
| `notes` | `notes_set_updated_at` | Before every update, sets `updated_at` to `now()` (function `public.set_updated_at()`) |

## Access (row-level security)

RLS is enabled on all four tables. Access needs both a table grant and a policy.

**Temporary open access.** Until per-user access is added, anyone with the publishable key can read and change every row:

| Table | Grants (`anon`, `authenticated`) | Policies |
|---|---|---|
| `notes` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | `notes: open select / insert / update / delete (temporary)`: all rows |
| `collections` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | `collections: open … (temporary)`: all rows |
| `tags` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | `tags: open … (temporary)`: all rows |
| `note_tags` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | `note_tags: open … (temporary)`: all rows |

These will be tightened when authentication is added: add a `user_id` column and policies that check `(select auth.uid()) = user_id`.

## Known issues

- **Rows are not tied to users.** No table has a `user_id`, and the open policies let anyone (even logged-out visitors) change or delete any row.
- **Leftover names on `collections`.** Its primary key (`notes_pkey`) and check constraint (`notes_title_check`) are named after `notes`. This suggests the table was renamed from an earlier `notes` table. The `notes` table's own primary key is therefore `notes_pkey1`.
- **Foreign keys without indexes.** `notes.collection_id` and `note_tags.tag_id` have no index. Listing a collection's notes, or finding all notes with a tag, will slow down as the tables grow.
- **The migrations can't rebuild these tables.** The four tables were created in the dashboard, and no file in `supabase/migrations/` creates them. Migration `20261124114513` only adds grants, policies and the trigger to existing tables. `npx supabase db pull` can generate a migration that captures the table definitions.

## Regenerating this document

Read-only queries with the Supabase CLI, for example:

```bash
npx supabase db query --remote --read-only -o table \
  "select table_name, column_name, data_type, is_nullable, column_default
   from information_schema.columns where table_schema = 'public'
   order by table_name, ordinal_position"
```

Also check:
- `pg_constraint`: keys, foreign keys, checks
- `pg_indexes`: indexes
- `pg_policies`: RLS policies
- `has_table_privilege()`: grants
- `pg_trigger`: triggers
